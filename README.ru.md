# PAPIRO — система помощи в реконструкции цифрового следа из открытых источников

PAPIRO — прототип OSINT-платформы для организации открытых данных, анализа совпадений между находками и построения кандидатных профилей и связей для последующей проверки исследователем. Важный принцип проекта — прослеживаемость: результаты должны сохранять сведения об источнике и не превращаться автоматически в утверждения о личности человека.

**Статус:** работающий прототип в разработке. Включает API, веб-интерфейс, хранение данных, сбор из выбранных открытых источников, детерминированную корреляцию и рабочее пространство исследования с графом. Это пока не универсальная OSINT-платформа и не готовый к промышленной эксплуатации продукт.

## Что уже реализовано

- Создание исследования и явный запуск поиска по имени.
- Запрос к текущим настроенным источникам: GitHub и Wikidata.
- Сохранение находок вместе с доступными URL и сведениями о происхождении.
- Извлечение индикаторов из открытых полей, возвращаемых источниками.
- Поиск точных совпадений нормализованных индикаторов из разных источников.
- Просмотр и оценка корреляций без автоматического подтверждения личности.
- Создание кандидатных профилей, привязка к ним находок и определение связей между профилями.
- Просмотр находок, индикаторов, корреляций, профилей и связей в интерфейсе исследования.
- Разграничение доступа к исследованиям с помощью учетных записей и ролей.

## Текущие ограничения

- Искусственный интеллект, языковые модели и машинное обучение не используются.
- Нет автономного итеративного поиска до исчерпания новых индикаторов.
- Система не выполняет универсальный поиск по всему Интернету и не гарантирует охват социальных сетей.
- Совпадение не доказывает, что находки относятся к одному человеку; это повод для дополнительной проверки.
- Систему не следует использовать как инструмент слежки, окончательной идентификации или автоматической проверки личности.
- Не все операции редактирования графа реализованы. Скрытие элемента в представлении не удаляет его из базы данных.
- Документация не утверждает, что платформа уже обладает достаточной безопасностью, производительностью или формальной проверкой для промышленной эксплуатации.

## Текущая архитектура

- **API и интерфейс:** FastAPI.
- **Асинхронная обработка:** Celery и Redis.
- **Основное хранилище:** PostgreSQL.
- **Визуализация графа:** Cytoscape.js в веб-интерфейсе.
- **Источники поиска по имени:** GitHub и Wikidata.
- **Корреляция:** детерминированный поиск точных совпадений нормализованных индикаторов между разными источниками.

Общий процесс:

`Исследование → явный запуск поиска → находки и индикаторы → корреляции → кандидатные профили и связи → оценка исследователя`

PostgreSQL хранит данные приложения, а Redis координирует асинхронные задачи. Neo4j, Elasticsearch и MinIO не входят в активный процесс, описанный текущей конфигурацией.

## Требования

- Git.
- Docker и Docker Compose.
- Доступ в Интернет для загрузки образов и обращения к открытым источникам.
- При необходимости — токен GitHub для увеличения лимитов API.

Текущий `docker-compose.yml` использует `network_mode: host` и адреса loopback. Конфигурация ориентирована на подготовленную среду разработки; для Docker Desktop в Windows/macOS и других сред развертывания может потребоваться изменение сетевых настроек. Не открывайте порты и службы для недоверенных сетей без предварительной проверки конфигурации.

## Локальная установка

Клонируйте репозиторий:

```bash
git clone https://github.com/Starv1ng/Kami-no-Eye.git
cd Kami-no-Eye
git switch main
```

Создайте файл окружения:

```bash
cp .env.example .env
```

В Windows PowerShell используйте `Copy-Item .env.example .env`.

Откройте `.env` и замените `AUTH_SECRET_KEY` собственным случайным секретом длиной не менее 32 символов. Его можно сгенерировать через Python:

```bash
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

Не добавляйте файл `.env` в репозиторий и не используйте секрет от другой установки. `GITHUB_TOKEN` необязателен; оставьте поле пустым, если токен не настраивается.

Соберите и запустите службы:

```bash
docker compose up --build -d
docker compose ps
docker compose logs --tail=100 api worker postgres redis
```

Ожидаемые локальные адреса:

- Интерфейс: http://127.0.0.1:8000/ui
- Документация API: http://127.0.0.1:8000/docs
- Проверка работоспособности: http://127.0.0.1:8000/health

Если запуск не удался, сначала изучите журналы и проверьте совместимость сетевой конфигурации Docker с операционной системой. В конфигурации разработки используются локальные учетные данные; измените их и проверьте настройки перед совместным или промышленным развертыванием.

## База данных и первая учетная запись администратора

При запуске приложение создает таблицы, соответствующие моделям, но это **не заменяет все миграции**, необходимые существующей базе данных или функциям идентификации, сущностей и совместной работы.

Перед миграцией базы с данными сделайте резервную копию и выясните, какие миграции уже применены. Не удаляйте том `pgdata` для устранения ошибок: в нем хранятся данные PostgreSQL.

Для новой базы изучите миграции и примените необходимые для текущей схемы. Документированный порядок включения текущих функций:

1. Применить `migrations/002_correlation_and_nomenclature.sql`.
2. Применить `migrations/003_entities_graph.sql`.
3. Выполнить `docker compose exec api python -m scripts.apply_identity_migration` для миграции идентификации 004.
4. Применить `migrations/006_investigation_sharing.sql`.
5. Применить `migrations/007_entity_accounts_and_verification.sql`.

SQL-миграции 002, 003, 006 и 007 можно применять из корня репозитория, например, так:

```bash
cat migrations/002_correlation_and_nomenclature.sql | docker compose exec -T postgres psql -U kami -d kami_eye
```

Повторите команду с нужным файлом миграции. Для миграции 004 используется приведенная выше команда Python. Если в базе уже есть данные, не запускайте миграции вслепую: сначала проверьте их содержимое и фактическую схему.

Создайте первого администратора **только после применения миграции идентификации**:

```bash
docker compose exec -it api python -m scripts.bootstrap_superuser
```

Скрипт запросит адрес электронной почты и пароль дважды. Минимальная длина пароля — 12 символов. Скрипт откажется работать, если в базе уже есть хотя бы одна учетная запись. Предустановленных демонстрационных учетных данных нет.

## Как проверить PAPIRO

1. Откройте http://127.0.0.1:8000/ui и войдите под действующей учетной записью.
2. Если на экземпляре включена публичная регистрация, создайте учетную запись исследователя. Запросы на институциональные учетные записи требуют одобрения администратора.
3. Создайте исследование в интерфейсе.
4. Вручную запустите поиск по имени. **Создание исследования само по себе не запускает сбор данных.**
5. Проверьте находки и их источники, индикаторы и предложенные корреляции.
6. Создайте кандидатный профиль, привяжите находки и определите связи, если есть основания их исследовать.
7. Оцените корреляции и связи как подтвержденные, отклоненные или неопределенные в соответствии с доступными вариантами. Запишите обоснование.
8. Откройте граф из рабочего пространства исследования и убедитесь, что элементы можно проследить до исходных доказательств.

Используйте только открытые данные и рассматривайте результаты как исследовательские гипотезы. Совпадения имени, псевдонима или индикатора недостаточно для установления личности.

## Автоматизированные тесты

Из корневого каталога проекта выполните:

```bash
docker compose run --rm api pytest -q
```

Результат зависит от версии кода, конфигурации и среды. Этот README не утверждает, что весь набор тестов проходит в текущем состоянии: запускайте тесты перед принятием изменений или развертыванием и анализируйте каждый сбой. Тесты с имитацией HTTP-ответов проверяют логику в контролируемых условиях, но не заменяют сквозную проверку с реальными службами.

## Безопасность и ответственное использование

- Установите сильный уникальный секрет в `.env` и никогда не публикуйте его.
- Не открывайте среду разработки напрямую в Интернет.
- Делайте резервную копию базы перед миграциями и изменением схемы.
- Сохраняйте происхождение доказательств и документируйте решения исследователя.
- Ограничивайте сбор открытой информацией и законными, разрешенными целями.
- Перед промышленным запуском проверьте аутентификацию, управление сессиями, ограничение частоты попыток, сеть, секреты, права доступа и политику хранения данных.
